# Prior-art research: Agent Skill + cost-tiered subagent composition

**Date of research:** 2026-07-28
**Completeness follow-up:** 2026-07-28 (same-day pass triggered by a completeness audit — see `search-log.md` §6 for what the audit found missing and why)
**Scope of this document:** `docs/research/**` only. This report, `evidence.csv`, and `search-log.md` are companion artifacts — every substantive claim below is backed by a row in [`evidence.csv`](./evidence.csv), and every search performed (including negative results) is logged in [`search-log.md`](./search-log.md).

## 1. Purpose and scope

This report surveys prior art relevant to a specific, composed pattern:

> A minimal **Agent Skill** is used *only* for progressive-disclosure discovery and routing by a parent LLM. When triggered, it invokes a **custom subagent** running on a cheaper/smaller model, with a **narrow tool allowlist**, an **isolated context window**, the ability to **write artifacts directly** (rather than streaming large content through the parent), and a **compact return value** back to the parent — all in service of reducing the parent model's token/credit consumption. The reference implementation targets **GitHub Copilot**, with **GPT-5.6 Sol** as the parent/orchestrator model and **Claude Haiku 4.5** as the specialist subagent model.

The goal of this research is narrow and evidentiary: to establish what has already been documented, by whom, and how it does or does not overlap with the composition above — **not** to assess patentability, novelty, or freedom to operate, and **not** to recommend an implementation. Legal clearance is explicitly out of scope.

## 2. Methodology

- **First-party sources first.** For every vendor/framework in scope (Anthropic/Claude, GitHub Copilot, OpenAI Agents SDK, LangChain/LangGraph and its Deep Agents harness, Google ADK, CrewAI, Microsoft Agent Framework and its legacy predecessors AutoGen/Semantic Kernel, and the Azure Architecture Center), the primary product or engineering documentation was fetched directly rather than relied upon via search-summary text.
- **Academic sources verified at the source.** Claims from FrugalGPT, RouteLLM, and AutoGen are drawn from the papers' own abstracts (fetched from arXiv), not from secondary summaries.
- **Gray literature clearly labeled.** Two informal/community sources are cited to establish that no settled naming convention exists for this composition; both are explicitly flagged as gray literature with lower confidence than first-party docs, and one is used specifically to illustrate a conflation this report intentionally avoids (see §5).
- **One low-confidence preprint flagged, not treated as established.** A very recent, non-peer-reviewed arXiv preprint on tool-schema overhead is cited only as a directional signal, with an explicit low-confidence flag (see §6).
- **Completeness audit and follow-up pass.** An initial research pass covered the vendors above but omitted two consequential first-party sources: LangChain's dedicated **Deep Agents** harness (a distinct, higher-level product from the base `langchain` multi-agent docs already cited) and **Microsoft Agent Framework** (the current framework Microsoft points migrators to from AutoGen and Semantic Kernel). A completeness audit flagged both omissions; this pass fetched and verified them directly, corrected a stale internal inconsistency in `evidence.csv` (row 20's caveat contradicted row 33, added in the prior pass — see `evidence.csv` row 20), and re-examined every "closest prior art" and "delegation-only" claim in all three files for staleness. See `search-log.md` §6 for the full audit trail.
- **Every row in `evidence.csv` records:** component/claim, title, org/author, URL, publication or last-updated date (or "accessed" date where a vendor doc has no visible revision date), source type, an exact quote or a clearly-labeled faithful paraphrase, a relevance tag (`direct` / `partial` / `component-only`), a confidence tag, and caveats.
- **Full query and catalog list** is in [`search-log.md`](./search-log.md), including explicit negative-result findings (no canonical name found, no direct academic measurement found for tool-schema token cost in isolation, etc.).

## 3. Closest prior art, by source

### 3.1 Anthropic / Claude — Agent Skills and Subagents (documented as *separate* mechanisms)

Anthropic documents **Agent Skills** and **Subagents** as two distinct, complementary features, and its own blog is explicit that they solve different problems:

- **Agent Skills** use a three-level progressive-disclosure model: at startup, the agent pre-loads only the `name`/`description` metadata of *every installed skill* into its system prompt — a real, if typically small, per-skill startup cost — and only loads a skill's full body when it is triggered, with bundled resource files loaded on demand thereafter. Because the body and bundled files need not be read into context up front, Anthropic states that "the amount of context that can be bundled into a skill is effectively unbounded" ([Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills), 2025-10-16, updated 2025-12-18) — note this claim is about the content bundled *within* a single skill, not about the number of skills that can be installed. This progressive-disclosure model is the direct antecedent of the "minimal skill used only for discovery/routing" half of the composition in scope.
- The open [Agent Skills specification](https://agentskills.io/specification) formalizes `SKILL.md` frontmatter (`name`, `description`, and an **experimental** `allowed-tools` field) as a portable format independent of any one vendor. This is also the specification LangChain's Deep Agents (§3.2), GitHub Copilot (§3.3), Google ADK (§3.5), CrewAI (§3.8), and Microsoft Agent Framework (§3.6) each state their own Skills implementation follows.
- **Subagents**, per Claude Code's own docs, each run "in its own context window with a custom system prompt, specific tool access, and independent permissions," and the same page recommends teams "control costs by routing tasks to faster, cheaper models like Haiku" ([Create custom subagents](https://code.claude.com/docs/en/sub-agents)).
- The same page's "Supported frontmatter fields" table goes further than a bare delegation mechanism: a single subagent's YAML frontmatter can set a `tools` field ("Tools the subagent can use... To preload Skills into context, use the `skills` field rather than listing `Skill` here"), a `model` field ("Model to use: `sonnet`, `opus`, `haiku`, `fable`, a full model ID... or `inherit`"), and a `skills` field ("Skills to preload into the subagent's context at startup. The full skill content is injected, not only the description") — all three on one subagent definition ([Create custom subagents](https://code.claude.com/docs/en/sub-agents), "Supported frontmatter fields"; see `evidence.csv` row 3 for the exact quotes). This is directly equivalent, at the schema level, to GitHub Copilot's `customAgents` configuration (§3.3) and CrewAI's `Agent` object (§3.8): each vendor documents a per-agent model override, a tool allowlist, and a `skills` field together on one subagent object. As with GitHub's and CrewAI's `skills` fields, Claude Code's `skills` frontmatter is a static list set by whoever *defines* the subagent, injecting full skill content at startup — not a minimal, relevance-triggered Skill that a parent model discovers via progressive disclosure and decides, at runtime, to use as the trigger for invoking the subagent. **LangChain's Deep Agents harness (§3.2) documents a superset of this same schema** — model, tools, and skills together on one `SubAgent` definition — and is the closest single documented match found in this research; see §3.2 for why it is foregrounded ahead of Claude Code and GitHub Copilot here.
- Anthropic's own comparison post describes Skills as "folders containing instructions, scripts, and resources that Claude discovers and loads dynamically when relevant to a task," while it describes Subagents as "specialized AI assistants with their own context windows, custom system prompts, and specific tool permissions" that "handle discrete tasks independently and return results to the main agent" — i.e., Anthropic itself treats these as two separate primitives, not one named composition ([Skills explained](https://claude.com/blog/skills-explained)).

**Relevance:** direct component-level prior art for *both halves* of the composition (skill-based progressive disclosure; subagent-based isolated, tool-restricted, cost-tiered delegation); also direct prior art, equivalent to GitHub Copilot's and CrewAI's schemas, for the static per-subagent model/tools/skills preload described above — but neither vendor's schema is the two mechanisms wired together as a single pattern.

### 3.2 LangChain Deep Agents — the closest documented structural match

LangChain publishes **Deep Agents** (`deepagents`), described as an ["agent harness"](https://docs.langchain.com/oss/python/deepagents/overview) distinct from the base `langchain` package's own multi-agent patterns (§3.7): "a higher-level harness built on LangChain that ships with subagents, skills, planning, a virtual filesystem, and context management" (LangChain's own Tip box pointing from its base multi-agent docs to Deep Agents; [Multi-agent](https://docs.langchain.com/oss/python/langchain/multi-agent); see `evidence.csv` row 37). Of every framework reviewed in this research, Deep Agents documents the largest number of elements of the target composition combined in one place, and is foregrounded here as **the closest comparator found — replacing GitHub Copilot and Claude Code as the "closest technical composition"** referenced in earlier drafts of this report (see §4, row "The skill and subagent wired together end-to-end as one pattern").

**Progressive-disclosure Skills.** Deep Agents Skills follow the open [Agent Skills specification](https://agentskills.io/specification) and use the same three-level model documented by Anthropic: "Skills use progressive disclosure: the agent loads skill information in layers instead of all at once. At startup, it sees only each skill's name and description. When a skill is invoked, it reads the full SKILL.md instructions. Supporting files load afterward, only when the instructions call for them." ([Skills](https://docs.langchain.com/oss/python/deepagents/skills); see `evidence.csv` row 36).

**A SubAgent schema combining model, tools, isolated skills, and a structured return.** Deep Agents' `SubAgent` definition (used via the harness's built-in `task` tool) documents, on one object, all of the following ([Subagents](https://docs.langchain.com/oss/python/deepagents/subagents); see `evidence.csv` row 35 for the exact field-table quotes):

- **`model`** — "Overrides the main agent's model. Omit to use the main agent's model," letting a subagent run on a different (and, by the vendor's own example code, cheaper/faster) model than the parent.
- **`tools`** — "Tools the subagent can use. Keep this minimal and include only what's needed... When specified, overrides the inherited tools entirely." This is the most explicit "keep it minimal" framing of a narrow tool allowlist found in any source reviewed in this research (compare Claude Code and GitHub Copilot, which frame tool restriction as capability scoping rather than explicit minimization — §4).
- **`skills`** — "Skills source paths. When specified, the subagent will load skills from these directories... This allows subagents to have different skill sets than the main agent... Skill state is fully isolated — a subagent's loaded skills are not visible to the parent, and vice versa." This is a stronger, more explicit isolation claim than any other vendor's subagent-level skills field: Claude Code, GitHub Copilot, and CrewAI each document a `skills` field on a subagent/agent object, but none of the three makes an explicit "not visible to the parent, and vice versa" isolation claim about skill state specifically.
- **`response_format`** — "Structured output schema for the subagent. When set, the parent receives the subagent's result as JSON instead of free-form text." (Documented on the dict/TypedDict-based `SubAgent`; the alternative `CompiledSubAgent` wrapper for custom LangGraph graphs does not expose this field, so it is not universal across every subagent type Deep Agents supports.)
- **Isolated context** — "Fresh context: Each invocation creates a new agent instance with its own context," combined with "Single handoff: It returns one final report to the main agent" and "Stateless messaging: Subagents are stateless and cannot send multiple messages back."

**Filesystem/artifact tools available to subagents.** Deep Agents' harness-level virtual filesystem tools (`ls`, `read_file`, `write_file`, `edit_file`, `delete`, `glob`, `grep`, and, on sandbox backends, `execute`) are available to the main agent and, by default, inherited by subagents; a subagent's filesystem access can be independently restricted via its own `FilesystemMiddleware(tools=[...])` instance in that subagent's `middleware` field ([Overview](https://docs.langchain.com/oss/python/deepagents/overview), "Virtual filesystem access"; [Subagents](https://docs.langchain.com/oss/python/deepagents/subagents), `middleware` field; see `evidence.csv` row 34, row 35). This is the closest documented match found in this research for "the subagent writes an artifact directly, bypassing the parent's context": a subagent can `write_file`/`edit_file` to the shared or its own scoped filesystem rather than returning large content through the parent's context, after which the parent (or a human) can reference the artifact by path. No source — including this one — frames this explicitly as a technique to reduce the *parent's* token consumption specifically; it is a general capability of the harness's tool surface, not a named "artifact bypass" feature.

**Determining whether `skills` is a static preload or an outer trigger.** The task's central open question — whether a subagent's `skills` are a static per-subagent availability list versus an outer Skill activation that itself triggers subagent invocation — is answered directly by the docs: it is the former, with a nuance. The **set** of skills a given subagent may draw from is a static, subagent-definition-time list of *source paths*, configured by whoever writes the `SubAgent` (identical in kind to Claude Code's, GitHub Copilot's, and CrewAI's static `skills` preload lists — §3.1, §3.3, §3.8). What is different is that, *within* that static set, Deep Agents preserves genuine runtime progressive disclosure at the subagent level — via the subagent's own independent `SkillsMiddleware` instance — rather than eagerly injecting full skill content at subagent startup the way Claude Code's and GitHub Copilot's subagent `skills` fields do. Neither of these is the outer linkage the composition in scope requires: **no language on the Subagents or Skills pages states that a skill's own invocation/activation is what causes the parent to invoke the subagent.** The trigger for invoking a subagent at all is the parent's own reasoning over the built-in `task` tool and the subagent's required `description` field ("Description of what this subagent does... The main agent uses this to decide when to delegate"), which is documented entirely separately from skill loading. Nothing in the docs prevents a `SKILL.md` body from *instructing* the agent to call `task()` — the same "usage choice, not a documented sub-feature" caveat already applied to GitHub Copilot and Claude Code (§3.3) applies here too.

**Relevance:** direct, and the strongest single documented match found for the overall shape of the composition in scope. Deep Agents combines cost-tiered model selection, an explicitly minimal/overridden tool allowlist, isolated context, isolated per-subagent progressive-disclosure skills, filesystem/artifact-write tools, and a structured compact return — on one subagent definition, in one harness, with LangChain's own docs recommending it as the built-in answer to "multi-agent." The one element it does **not** document is the specific outer runtime linkage in which a minimal Skill's own activation is itself what instructs/causes the parent to invoke the subagent; see §4 and §8 for how this narrows, but does not eliminate, the differentiating gap identified in this report.

### 3.3 GitHub Copilot — custom agents, Agent Skills, and sub-agent orchestration (the reference platform)

GitHub's own docs describe **custom agents** that the parent model can invoke as isolated sub-agents, each with its own scoped tool list and instructions ([Custom agents and sub-agent orchestration](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/custom-agents)). The Copilot CLI docs state: "The AI model being used by the CLI can choose to delegate a task to a subsidiary subagent process, that operates using a custom agent with specific expertise, if it judges that this would result in the work being completed more effectively." ([Invoking custom agents](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/invoke-custom-agents)).

GitHub Copilot also documents a separate **Agent Skills** mechanism: "Agent skills are folders of instructions, scripts, and resources that Copilot can load when relevant to improve its performance in specialized tasks. The Agent Skills specification is an open standard, used by a range of different AI systems." ([About agent skills](https://docs.github.com/en/copilot/concepts/agents/about-agent-skills)). The companion how-to page confirms the same `SKILL.md` name/description/`allowed-tools` frontmatter format as the open spec ([Adding agent skills for GitHub Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-skills)). This means **GitHub Copilot documents both halves individually** — a Skill-equivalent, relevance-triggered discovery mechanism, and a separate subagent/delegation mechanism — the same pattern documented by Anthropic, LangChain (both Deep Agents and the base library), Google ADK, CrewAI, and Microsoft Agent Framework (see §3.1, §3.2, §3.5, §3.7, §3.8, §3.6, §4, §8), though on GitHub's docs the two are likewise presented as separate features on separate pages, not one composed pattern.

The custom-agents SDK reference goes further than a bare delegation mechanism: its per-agent configuration table documents both a `model` field ("Model identifier to use while this agent runs") and a `skills` field ("Skill names to preload into the agent's context at startup") on the same agent object as the `tools` allowlist. GitHub states plainly that you can "Set `model` and `reasoningEffort` to override the parent session's model settings while a custom agent runs," and that when `skills` is set, "the full content of each listed skill is eagerly injected into the agent's context at startup — the agent doesn't need to invoke a skill tool; the instructions are already present" (skills are "opt-in" and "sub-agents do not inherit skills from the parent") ([Custom agents and sub-agent orchestration](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/custom-agents), "Configuration reference" and "Per-agent skills" sections; see `evidence.csv` row 29 for the exact quotes). This schema — a cheaper/different model, a tool allowlist, and skill content combined on one subagent definition — is one of **three** directly documented equivalents found in this research, alongside Claude Code's subagent frontmatter (§3.1) and CrewAI's `Agent` object (§3.8), all three of which independently support the same `model`/`tools`/`skills` combination with skill content fully or automatically loaded at startup. **LangChain's Deep Agents `SubAgent` (§3.2) documents a superset of this same shape** — the same three fields plus explicit skill-state isolation and a structured `response_format` — and is accordingly foregrounded as the closest overall match in this report; GitHub Copilot, Claude Code, and CrewAI remain equivalent prior art *to each other* on this narrower schema-combination point, and none of the three is uniquely positioned relative to the other two. It is not, however, the same mechanism as the composition in scope: the `skills` preload here is a static list set by whoever *defines* the agent, eagerly injecting full skill content at agent startup — not a minimal, relevance-triggered Skill that a parent model discovers via progressive disclosure and decides, at runtime, to use as the trigger for invoking the subagent (that triggered-discovery role is filled by Copilot's separate Agent Skills feature described above, which is not documented as feeding into `customAgents.skills`).

Both models named in the target composition are confirmed generally available in Copilot: **GPT-5.6 Sol** and **Claude Haiku 4.5** ([Supported AI models in GitHub Copilot](https://docs.github.com/en/copilot/reference/ai-models/supported-models)). GitHub's changelog positions Sol as the highest-reasoning (and by implication priciest) tier of the GPT-5.6 family ([changelog, 2026-07-09](https://github.blog/changelog/2026-07-09-openais-gpt-5-6-sol-terra-and-luna-are-now-available-in-github-copilot/)).

**Measured pricing (not inferred):** GitHub's own billing reference lists per-token prices directly: GPT-5.6 Sol is priced well above Claude Haiku 4.5 at the ≤272K context tier ([Models and pricing for GitHub Copilot](https://docs.github.com/en/copilot/reference/copilot-billing/models-and-pricing)). This is the strongest first-party, dated, *measured* evidence for the "cheaper specialist model" economic rationale in the target composition — see `evidence.csv` row 9 for the exact figures quoted at time of research.

**Relevance:** direct architectural prior art for the parent→custom-subagent mechanism this repository is built on; direct, measured confirmation of the cost differential between the two named models; direct evidence that GitHub documents a Skill-equivalent discovery mechanism as well; and, together with Claude Code and CrewAI (§3.1, §3.8), one of three documented single-schema compositions found in this research of per-agent model override, tool restriction, and skill content together — though Deep Agents (§3.2) documents a more complete version of the same idea. GitHub's docs do not, however, describe a named "skill triggers subagent" composition, and the `skills` field's eager, statically-configured preload is a different mechanism from a relevance-triggered Skill deciding at runtime to invoke a subagent — so the differentiating gap is the absence of that named, progressive-disclosure-triggered pattern, not an absence of underlying model/skill composition capability, and that gap applies equally to Claude Code's, CrewAI's, and (per §3.2) Deep Agents' equivalent schemas.

### 3.4 OpenAI Agents SDK — Handoffs and Agents-as-tools

OpenAI's SDK documents two related but distinct multi-agent mechanisms: **Handoffs**, where control fully transfers to another agent (represented internally as a callable tool) ([Handoffs](https://openai.github.io/openai-agents-python/handoffs/)), and **Agents-as-tools**, where a "manager" agent retains control and calls specialist agents as tools, receiving their output back into its own context ([Agent orchestration](https://openai.github.io/openai-agents-python/multi_agent/)). Each agent can be assigned an independent `model`, permitting a cheaper model for a specialist ([Agents](https://openai.github.io/openai-agents-python/agents/)).

**Relevance:** partial — the agents-as-tools pattern (parent retains control, specialist returns a result, per-agent model choice) is architecturally close to the "compact return to parent" and "cheaper specialist model" elements, but OpenAI's docs have no analog to Anthropic-style progressive-disclosure Skills as the *trigger* mechanism. Of every framework/product reviewed in this research, OpenAI's Agents SDK is one of only three (alongside Microsoft's legacy AutoGen and Semantic Kernel, §3.6) for which no Skill-equivalent progressive-disclosure mechanism was found documented at all.

### 3.5 Google Agent Development Kit (ADK) — coordinator/sub-agent "modes"

Google's ADK documents a coordinator agent delegating to sub-agents, with an explicit `mode` parameter controlling how much of the sub-agent's interaction/output flows back to the coordinator (e.g., a scoped, single-turn mode vs. a full conversational hand-off) ([Build collaborative agent teams](https://adk.dev/workflows/collaboration/)). The same page documents explicit context isolation for scoped-mode subagents: "Each `task` or `single-turn` mode agent operates in its own isolated session branch. When these agents operate in parallel, each agent only sees events from its own branch when building context for AI model calls, and cannot see what its peer agents are doing. Once all parallel branches complete, the parent agent receives the collected results and can proceed." This isolation is documented specifically for the `task` and `single_turn` modes. The page describes `chat` as full interaction with manual return but does not state whether `chat` uses an isolated session branch, so this report makes no isolation claim for that mode (see `evidence.csv` row 30 for the exact quote).

ADK also documents a **separate** Skills mechanism, on its own doc page, that is a direct match for the "Skill-equivalent progressive-disclosure discovery" half of the composition: an agent's `SkillToolset` loads a Skill's `name`/`description` metadata (L1) at startup for discovery, loads the Skill's full body instructions (L2) only "when the Skill is triggered by the agent," and loads bundled reference/asset/script files (L3) "as needed" — "the structure of a Skill allows it to be loaded incrementally to minimize the impact on the operating context window of the agent" ([Skills for ADK agents](https://adk.dev/skills/); this page was added 2026-02-13 per the docs repository's commit history, i.e. before the reference-implementation date of this report; see `evidence.csv` row 32 for the exact quotes).

**Relevance:** partial-to-direct — the scoped-return-value concept overlaps with "compact return," and ADK's `task`/`single_turn`-mode isolated session branches are a direct match for the "isolated context window" element of the composition (alongside Claude Code, GitHub Copilot, LangChain subagents, and Deep Agents subagents, §4/§8). ADK's Skills docs are also direct prior art for the progressive-disclosure discovery half. However, these are two separate, separately documented ADK features: the Skills page describes a `SkillToolset` that augments a *single* agent's own tool list (`list_skills`/`load_skill`/`load_skill_resource`); it is not documented as a mechanism that triggers the coordinator/subagent delegation described on the collaboration page above. No source was found stating that triggering an ADK Skill causes the parent to invoke a `task`/`single_turn`/`chat`-mode subagent — so, like Anthropic, LangChain, GitHub Copilot, CrewAI, and Microsoft Agent Framework (§4, §8), ADK documents *both* halves of the composition, but not the two wired together as one pattern.

### 3.6 Microsoft — Agent Framework (current), and legacy AutoGen / Semantic Kernel / Azure Architecture Center

Microsoft's current, actively developed framework is **Agent Framework**, for which Microsoft publishes dedicated guides to "Migrate from Autogen" and "Migrate from Semantic Kernel" ([Agent Framework documentation](https://learn.microsoft.com/en-us/agent-framework/); see `evidence.csv` row 38) — i.e., Agent Framework, not AutoGen or Semantic Kernel, is the current target for anyone building on Microsoft's agent stack today. This distinction matters for this report because Agent Framework documents a Skill-equivalent progressive-disclosure mechanism that its legacy predecessors do not.

**Agent Framework's Agent Skills.** Agent Framework documents its own **Agent Skills** feature, on a doc page separate from its multi-agent orchestration docs, using a four-stage progressive-disclosure pattern: "1. **Advertise** (~100 tokens per skill) - Skill names and descriptions are injected into the system prompt at the start of each run... 2. **Load** (< 5000 tokens recommended) - When a task matches a skill's domain, the agent calls the `load_skill` tool to retrieve the full SKILL.md body with detailed instructions. 3. **Read resources** (as needed)... 4. **Run scripts** (as needed)..." ([Agent Skills](https://learn.microsoft.com/en-us/agent-framework/agents/skills); see `evidence.csv` row 39 for the exact quotes). This is implemented as a per-agent context provider (`AgentSkillsProvider` in C#, `SkillsProvider` in Python) — a single-agent feature, not one wired to any multi-agent mechanism. Microsoft's own docs make the separateness explicit in a dedicated section: "Agent Skills and Agent Framework Workflows both extend what agents can do, but they work in fundamentally different ways... With a skill, the AI decides how to execute the instructions... With a workflow, you explicitly define the execution path... Workflows are better suited for multi-step business processes that coordinate multiple agents" (same page, "When to use skills vs. workflows"). This makes **Microsoft Agent Framework the sixth framework found in this research to document a Skill-equivalent progressive-disclosure mechanism**, alongside Anthropic, LangChain (Deep Agents and the base library), GitHub Copilot, Google ADK, and CrewAI (§3.1, §3.2, §3.7, §3.3, §3.5, §3.8) — and, like every one of those five, Agent Framework documents its Skills feature and its delegation/orchestration features on separate pages, not as one composed pattern.

**Agent Framework's delegation/orchestration surfaces.** Agent Framework's **Workflows** layer documents "built-in patterns for coordinating multiple AI agents, including sequential, concurrent, hand-off, and magentic" orchestration ([Microsoft Agent Framework Workflows](https://learn.microsoft.com/en-us/agent-framework/workflows/); see `evidence.csv` row 40), and a separate **Agents as Tools** pattern lets "one agent (the *outer* agent)... call another agent (the *inner* agent) as if it were a regular function tool," where "each inner agent has a tight scope — its own instructions, its own tools, its own expertise," and, per the page's own tip, "each agent can also use a different model depending on its specialization and requirements... simpler agents might use smaller, faster models for efficiency" ([Agents as Tools](https://learn.microsoft.com/en-us/agent-framework/journey/agents-as-tools); see `evidence.csv` row 41). The same page documents context isolation explicitly: "The inner agent runs with its own instructions and tools. It doesn't automatically inherit the outer agent's conversation history or context," and a compact return: "The outer agent sees the inner agent's final text response — it doesn't see the inner agent's intermediate reasoning, tool calls, or context." Microsoft's own **Handoff** orchestration docs draw an explicit first-party contrast against this pattern: "In handoff orchestration, control is explicitly passed between agents based on defined rules... There is no central authority managing the workflow. In contrast, agent-as-tools involves a primary agent that delegates sub tasks to other agents and once the agent completes the sub task, control returns to the primary agent," and on context: "In handoff orchestration, the conversation is handed off to another agent entirely. The receiving agent has full context of what has been done so far. In agent-as-tools, the primary agent manages the overall context and might provide only relevant information to the tool agents as needed" ([Microsoft Agent Framework Workflows Orchestrations - Handoff](https://learn.microsoft.com/en-us/agent-framework/workflows/orchestrations/handoff), "Differences Between Handoff and Agent-as-Tools"; see `evidence.csv` row 42). This is the same Handoffs-vs-Agents-as-tools distinction OpenAI's SDK documents (§3.4), independently confirmed by Microsoft's current framework.

**No combined schema found.** Unlike Claude Code, GitHub Copilot, CrewAI, and LangChain's Deep Agents (§3.1, §3.3, §3.8, §3.2), no source was found in Agent Framework's Agents-as-Tools or Handoff docs that combines a `model` override, a `tools` allowlist, and `skills` content on one documented agent/inner-agent object — the Agents as Tools page's own "Considerations" table covers model, tools, and context isolation, but does not mention Skills at all. Agent Framework therefore sits with Anthropic-as-a-whole, the base LangChain library, and Google ADK: it documents *both* halves of the composition (Skills, and cost-tiered/isolated delegation) on separate pages, but with no single documented schema combining all three (model/tools/skills) the way Claude Code, GitHub Copilot, CrewAI, and Deep Agents do.

**Legacy AutoGen and Semantic Kernel remain delegation-only.** The findings from the original research pass for Microsoft's legacy frameworks are unchanged and remain accurate for those specific products, but must not be read as a blanket claim about "Microsoft" now that Agent Framework's own Skills page is confirmed:

- **AutoGen** documents a "Handoffs" design pattern and explicitly attributes the handoff concept's lineage to OpenAI's experimental "Swarm" project, not to Microsoft itself ([Handoffs (AutoGen Core)](https://microsoft.github.io/autogen/stable/user-guide/core-user-guide/design-patterns/handoffs.html)) — useful component-level lineage evidence, but not on point for the skill+cost-tier composition. **This page's own reference implementation is not an isolated-context pattern:** the `UserTask` message it hands off explicitly carries `context: List[LLMMessage]` — the full running conversation history — to the next agent, so control transfers along with shared context rather than the receiving agent starting in a clean, isolated context window. This is a meaningful difference from the isolated-context property documented for Claude Code, GitHub Copilot, LangChain subagents, Deep Agents subagents, and ADK's scoped modes (see §4 and §8). No Skill-equivalent progressive-disclosure mechanism was found documented for AutoGen in the pages reviewed.
- **Semantic Kernel**'s Handoff Orchestration is explicitly marked **experimental** and lets agents transfer control based on conversational context ([Handoff Agent Orchestration](https://learn.microsoft.com/en-us/semantic-kernel/frameworks/agent/agent-orchestration/handoff)). No Skill-equivalent progressive-disclosure mechanism was found documented for Semantic Kernel in the pages reviewed.
- Azure's **Architecture Center** frames multi-agent orchestration as justified only above a stated complexity threshold — i.e., a single agent with tools is the recommended default, and multi-agent delegation is presented as an escalation, not a default pattern ([AI Agent Orchestration Patterns](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns)).

**Relevance:** for Agent Framework specifically — direct prior art for the Skill-equivalent progressive-disclosure half, and direct/measured-adjacent prior art (per-agent model, tool scope, context isolation, compact return) for the cost-tiered subagent half via Agents as Tools, though the two remain undocumented as a combined schema and undocumented as wired together. For legacy AutoGen, Semantic Kernel, and the Azure Architecture Center — component-only to partial, as in the original research pass: none of these three legacy sources document a Skill-style discovery/trigger layer feeding a cost-tiered subagent, and AutoGen's Handoffs pattern is explicitly not context-isolated.

### 3.7 LangChain / LangGraph (base library) — the clearest documented separation of "Skills" and "Subagents"

LangChain's own base multi-agent documentation (distinct from the Deep Agents harness in §3.2) is the single clearest piece of first-party evidence that **"Skills" and "Subagents" are treated as two separate, independently named patterns** by at least one major agent framework, not components of one composed pattern: its overview page lists "Subagents" and "Skills" as distinct rows in a pattern-comparison table ([Multi-agent](https://docs.langchain.com/oss/python/langchain/multi-agent)). Its dedicated Subagents page describes them as stateless, tool-invoked, and context-isolated from the main conversation ([Subagents](https://docs.langchain.com/oss/python/langchain/multi-agent/subagents)) — closely matching the "isolated context" element of the target composition.

Re-verified for this update, the same overview page now also carries a first-party Tip that explicitly points from this base-library separation to Deep Agents as the bundled alternative: "For built-in multi-agent support, use Deep Agents: a higher-level harness built on LangChain that ships with subagents, skills, planning, a virtual filesystem, and context management" (see `evidence.csv` row 37). In other words, LangChain's own docs simultaneously (a) treat Subagents and Skills as separate patterns in the base library, and (b) recommend Deep Agents (§3.2) as the harness where those same two concepts are combined into one configuration surface — reinforcing why Deep Agents, not the base library, is this report's foregrounded closest comparator.

**Relevance:** direct — this remains the strongest single piece of evidence supporting the terminology conclusion in §7 for the base `langchain` package: an established framework explicitly documents these as two separate mechanisms within that package, reinforcing that no canonical combined name exists at that layer — while pointing to its own Deep Agents harness (§3.2) as the place where they are combined.

### 3.8 CrewAI — per-agent delegation, per-agent LLM choice, and a separate Skills mechanism

CrewAI agents can delegate tasks to other agents via an `allow_delegation` flag, and each agent can be configured with an independent `llm`, permitting a cheaper model for a delegate agent ([Agents](https://docs.crewai.com/v1.15.8/en/concepts/agents.md)).

CrewAI **also** documents a separate Skills mechanism with its own `SKILL.md` format (name/description/`allowed-tools` frontmatter over a markdown body, matching the open Agent Skills spec) that its own docs describe as using **progressive disclosure**: a `discover_skills()` stage loads only "Name, description, frontmatter fields," and a subsequent `activate_skill()` stage loads the "Full SKILL.md body text" ([Skills](https://docs.crewai.com/v1.15.8/en/concepts/skills.md); see `evidence.csv` row 33 for the exact quotes). The Skills page also shows `skills` and `tools` set together on one `Agent()` call, and the companion Agents page documents `llm` as an independent per-agent attribute — i.e., CrewAI documents `llm`, `skills`, and `tools` as three combinable Agent attributes, the same shape (though a different vendor) as Claude Code's subagent frontmatter, GitHub Copilot's `customAgents` schema, and LangChain Deep Agents' `SubAgent` (§3.1, §3.3, §3.2).

Two important caveats limit how far this goes, however. First, as CrewAI's own docs state, the two-stage discover/activate split "only matters when using the programmatic API" — in the common `Agent(skills=["./skills"])` usage, skills are "automatically discovered and activated" together, i.e. eagerly, not one at a time by runtime relevance; this is closer to Claude Code's and GitHub Copilot's static, eager `skills` preload (§3.1, §3.3) than to a minimal, relevance-triggered discovery layer that decides at runtime whether to fire, and than to Deep Agents' subagent-level skills, which preserve genuine progressive disclosure within their static availability list (§3.2). Second, CrewAI's `allow_delegation` flag is a separate, independently configured mechanism; no source was found stating that a CrewAI skill's discovery or activation itself decides, at runtime, to delegate to a different (cheaper-model) agent.

**Relevance:** partial-to-direct — direct for the "different agents, different model tiers" element (`llm`) and for the Skill-equivalent progressive-disclosure discovery layer (`discover_skills()`/`activate_skill()`); still no source documents that a CrewAI skill's activation is itself the trigger for `allow_delegation`-based delegation to another agent.

### 3.9 Academic literature — cost routing and multi-agent frameworks (component-level only)

- **FrugalGPT** demonstrates that cascading across LLMs of different cost tiers can match or exceed the accuracy of always using the most expensive model, while cutting cost by up to 98% in some experiments ([arXiv:2305.05176](https://arxiv.org/abs/2305.05176), 2023-05-09).
- **RouteLLM** shows a learned router that dynamically chooses between a strong and weak model can cut serving costs by more than 2x with limited quality loss ([arXiv:2406.18665](https://arxiv.org/abs/2406.18665), 2024-06-26).
- **AutoGen** presents an open-source framework for customizable, conversable multi-agent applications ([arXiv:2308.08155](https://arxiv.org/abs/2308.08155), 2023-08-16).

**Relevance:** component-only. These papers substantiate the general principle that routing between model cost tiers reduces spend without necessarily sacrificing quality, and that multi-agent conversation frameworks are an established research area — but none study a Skill-triggered discovery/trigger layer as part of the routing decision, and none focus on tool-schema/context minimization specifically.

### 3.10 Context engineering and tool-schema minimization (measured vs. inferred — see §5–6)

- Anthropic's own context-engineering guidance argues that curating a small, high-signal tool set is a **context-engineering** concern — bloated tool sets create "ambiguous decision points" for the model — distinct from access-control framing ([Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)).
- LangChain's Deep Agents docs frame subagent delegation itself in the same terms: "Subagents solve the context bloat problem. When agents use tools with large outputs (web search, file reads, database queries), the context window fills up quickly with intermediate results. Subagents isolate this detailed work — the main agent receives only the final result, not the dozens of tool calls that produced it." ([Subagents](https://docs.langchain.com/oss/python/deepagents/subagents); see `evidence.csv` row 35) — a first-party statement of the context-minimization rationale for delegation itself, independent of Anthropic's.
- Chroma's **Context Rot** report provides controlled measurements showing that LLM performance degrades non-uniformly as input length grows, even on simple tasks, across 18 models tested ([Context Rot](https://www.trychroma.com/research/context-rot)) — supporting the general "more context/tokens can hurt, not just cost more" rationale, though it measures overall input length rather than tool-schema tokens specifically.
- A very recent, non-peer-reviewed preprint proposes "dynamic tool gating and lazy schema loading" specifically to reduce per-turn tool/MCP schema token overhead ([arXiv:2604.21816](https://arxiv.org/abs/2604.21816), 2026-04) — the closest match found to a direct, quantified claim about tool-schema cost, but flagged low-confidence (see §6).

### 3.11 Gray literature — no settled informal name found

Two representative community sources were fetched directly (not merely summarized via search):

- A practitioner blog post with a concrete token/pricing breakdown recommends running "planner" agents on a stronger model and "worker" subagents on Haiku-tier models to control spend ([Why Claude Code Subagents Burn So Many Tokens](https://youcanbuildthings.com/articles/claude-code-subagents-token-usage/)) — directly on point for the cost-routing rationale, medium confidence as an informal source.
- A second blog post describes subagents informally as "a team of specialists" with restricted tool access, explicitly citing **both** improved focus and improved safety in the same breath ([A practical guide to subagents in Claude Code](https://www.eesel.ai/blog/subagents-in-claude-code)) — cited specifically to illustrate the conflation this report intentionally avoids (§5), and marked low confidence.

Beyond these two, extensive searching (see `search-log.md` §5) found no consistent informal name for the composed pattern.

## 5. Context minimization vs. least privilege/safety — a deliberate distinction

The task underlying this composition asks specifically that tool restriction be understood as **context minimization**: fewer tool definitions/schemas loaded into the subagent's prompt means fewer tokens spent on schemas, fewer choices for the model to reason over, and typically more compact tool outputs — as distinct from **least privilege/safety**, i.e., restricting tools to prevent unwanted or unsafe actions. Both are legitimate benefits, but they are different justifications, and sources vary in which one (or both) they foreground:

- Anthropic's context-engineering guidance foregrounds the **context-minimization** framing: it discusses tool-set bloat primarily as a problem of "ambiguous decision points" and a finite "attention budget" that "every new token introduced depletes," not primarily as a safety control (`evidence.csv` row 24).
- LangChain's Deep Agents docs foreground the same framing for delegation itself, not just tool count: "Subagents solve the context bloat problem... Subagents isolate this detailed work — the main agent receives only the final result" (`evidence.csv` row 35), and separately frame the `tools` field on a `SubAgent` as something to "keep... minimal" (`evidence.csv` row 35) — the clearest explicit minimization framing for a subagent's tool allowlist found in this research.
- Claude Code's subagent docs, GitHub Copilot's custom-agent docs, and Microsoft Agent Framework's Agents-as-Tools docs describe tool restriction mainly as **scoping capability/expertise** for a subagent/inner agent — this is adjacent to both framings but does not explicitly separate them (`evidence.csv` rows 3, 6, 41).
- The `eesel.ai` gray-literature post is quoted specifically because it **conflates** the two rationales in a single sentence — restricted tool access described as improving both "focus" and "safety" simultaneously (`evidence.csv` row 28). This is included deliberately to demonstrate why this report treats them as separate claims rather than assuming the sources already do.

**Conclusion on this point:** the context-minimization rationale for tool restriction is supported qualitatively by first-party sources (Anthropic's context-engineering post, and LangChain's Deep Agents docs for delegation and tool-allowlisting specifically) but is **not accompanied by a precise, verified, first-party measurement** of how many tokens a given tool schema costs, or how much accuracy improves per removed tool. The least-privilege/safety rationale is well established as a separate, secondary benefit across the security literature generally, but that literature was not the focus of this search and is not itself cited here as a primary claim.

## 6. Measured vs. inferred: schema-token cost claims

Per the task's requirement to flag which schema-token claims are measured versus inferred:

- **Measured (first-party, dated, directly quoted):** the per-token price differential between GPT-5.6 Sol and Claude Haiku 4.5 in GitHub Copilot's own billing documentation (`evidence.csv` row 9). This is a real, dated, vendor-published number, not an estimate.
- **An approximate, first-party per-skill figure (not a rigorous study):** Microsoft Agent Framework's Skills docs state its metadata-advertisement stage costs "~100 tokens per skill" and recommend keeping a skill's full body under "< 5000 tokens" (`evidence.csv` row 39). This is a concrete, vendor-published estimate specifically about skill-advertisement overhead (closer to the composition's tool/skill-schema question than the Sol/Haiku pricing figure above) but is presented as rule-of-thumb guidance, with no disclosed measurement methodology, sample size, or model tested — it is treated here as a directional, low-rigor data point, not a controlled measurement.
- **Measured, but about input length generally, not tool schemas specifically:** Chroma's Context Rot report measures performance degradation as a function of total input tokens, across 18 models, in controlled conditions (`evidence.csv` row 25). This substantiates "more tokens in context can hurt," but does not isolate tool-schema tokens as a variable.
- **Inferred / qualitative, not a number:** Anthropic's context-engineering guidance argues that large tool sets increase ambiguity and consume attention budget, but does not publish a specific token-per-tool-schema figure (`evidence.csv` row 24).
- **Preliminary and unverified (flagged explicitly low-confidence):** the arXiv 2604.21816 preprint is the only source found that directly proposes measuring/eliminating a "tools tax" from schema loading, but it is a very recent (April 2026), non-peer-reviewed preprint, verified here only at the title/abstract level, and should not be treated as an established result (`evidence.csv` row 26).

**Net assessment:** the claim "a narrower tool allowlist reduces the subagent's context/token footprint" is well supported directionally by first-party qualitative guidance (now from two vendors — Anthropic and LangChain) and by general context-length-degradation research, and the cost differential between the two named models is directly measured — but a precise, verified, first-party quantification of *tool-schema-specific* token savings was not found in any peer-reviewed or vendor-published source at the time of this research. Microsoft's "~100 tokens per skill" figure is the closest thing to a quantified, first-party number for *skill* (not tool) schema overhead found, and it is explicitly treated here as approximate guidance rather than a measurement.

## 7. Terminology recommendation

No source examined — vendor documentation, open specification, pattern catalog, academic paper, or gray literature — uses a single, settled name for the full composition described in §1 (skill-as-discovery/trigger, feeding a cost-tiered, tool-restricted, context-isolated subagent, with a compact return). The clearest evidence for this is LangChain's own base-library documentation, which lists "Subagents" and "Skills" as two separate rows in its multi-agent pattern comparison, rather than as one pattern (`evidence.csv` row 18) — while, in the same breath, pointing readers to its own **Deep Agents** harness as the bundled alternative (`evidence.csv` row 37). This is reinforced by every other framework found to document a Skill-equivalent progressive-disclosure mechanism at all — Anthropic, GitHub Copilot, Google ADK, CrewAI, and Microsoft Agent Framework each publish their Skills-equivalent feature and their subagent/delegation feature on separate documentation pages, never as one named pattern (§3.1, §3.3, §3.5, §3.8, §3.6). Even Deep Agents, which comes closest to combining the underlying mechanisms into one configuration object, does not name the resulting shape as a single pattern distinct from "a subagent that happens to have skills" — and, critically, does not document a Skill's own activation as the trigger for invoking that subagent (§3.2).

Consistent with the evidence gathered, this report recommends describing the pattern as:

> **A repository-local composition of established mechanisms** — a progressive-disclosure Agent Skill used as a discovery/trigger layer, combined with a cost-tiered, tool-restricted, context-isolated custom subagent — **for which no canonical or industry-standard name was found in the sources searched**, and for which LangChain's Deep Agents harness is the closest documented single-schema composition of the *subagent* half (model, tools, isolated skills, artifact writes, structured return) found, without documenting the specific Skill-activation-triggers-subagent linkage that defines the outer composition.

This is a terminology observation, not a novelty claim (see §8).

## 8. Conclusion

The individual mechanisms that make up this composition are each well precedented:

- Progressive-disclosure Agent Skills as a low-context discovery/trigger layer are documented by Anthropic, formalized in the open Agent Skills specification, and independently documented (with the same metadata-first/body-on-demand shape) by **LangChain's Deep Agents harness**, **Google ADK's `SkillToolset`**, **CrewAI's `discover_skills()`/`activate_skill()`** API (which CrewAI's own docs label "progressive disclosure"), and **Microsoft Agent Framework's four-stage Agent Skills feature** (advertise/load/read-resources/run-scripts). GitHub Copilot documents the same specification's `SKILL.md` format for its own separate Agent Skills feature. That is six frameworks/vendors — **Anthropic, GitHub Copilot, LangChain (base library and Deep Agents), Google ADK, CrewAI, and Microsoft Agent Framework** — confirmed in this research to document a Skill-equivalent progressive-disclosure mechanism, each on a page separate from that same vendor's delegation/subagent mechanism.
- Isolation, tool restriction, and cost-tiered model selection for a delegated agent are each independently documented — but not uniformly all three together — across the frameworks surveyed. Specifically, per what each cited page actually states:
  - **Isolated context window:** explicitly documented for Anthropic/Claude Code subagents, GitHub Copilot custom agents, LangChain's base-library Subagents, **LangChain Deep Agents subagents** ("Fresh context: Each invocation creates a new agent instance with its own context"), Google ADK's `task`/`single_turn`-mode subagents (each "operates in its own isolated session branch" and "cannot see what its peer agents are doing"), and **Microsoft Agent Framework's Agents-as-Tools pattern** ("doesn't automatically inherit the outer agent's conversation history or context"). The cited ADK page does not state whether `chat` uses an isolated branch. By contrast, OpenAI's Handoffs and **Microsoft Agent Framework's own Handoff orchestration** both transfer the active conversation to the specialist (not isolated) — Microsoft's docs state this contrast against Agents-as-Tools explicitly in its own words — and AutoGen's Handoffs reference implementation explicitly passes the full conversation history to the next agent (`context: List[LLMMessage]`) rather than isolating it.
  - **Narrow tool allowlist:** explicitly documented for Anthropic/Claude Code subagents, GitHub Copilot custom agents, the Agent Skills spec's experimental `allowed-tools` field (which CrewAI's own SKILL.md format also carries, though CrewAI's docs note this field "does not provision or inject any tools" and is experimental metadata only), and **LangChain Deep Agents' `SubAgent.tools`**, whose "keep this minimal and include only what's needed" phrasing is the single most explicit token-minimization framing of a tool allowlist found in this research. Not confirmed as an explicit subagent-level "narrow allowlist" claim in the OpenAI Agents SDK, Google ADK, CrewAI, AutoGen, Semantic Kernel, or Microsoft Agent Framework's Agents-as-Tools/Handoff pages reviewed (the last of these scopes an inner agent to "its own tools" without an explicit minimization framing).
  - **Independent/cheaper model selection:** explicitly documented for Anthropic/Claude Code subagents (naming Haiku directly), GitHub Copilot custom agents (per-agent `model` field, documented to "override the parent session's model settings while a custom agent runs"), OpenAI's Agents SDK (per-agent `model` field), CrewAI (per-agent `llm` field), **LangChain Deep Agents** (`SubAgent.model`), and **Microsoft Agent Framework's Agents-as-Tools** ("simpler agents might use smaller, faster models for efficiency"). Not confirmed as an explicit claim on the Google ADK, AutoGen Handoffs, or Semantic Kernel Handoff pages reviewed in this research.
  - **Model + skill composition on a single agent/subagent definition:** GitHub Copilot's `customAgents` schema, Claude Code's subagent frontmatter, CrewAI's `Agent` object, and **LangChain Deep Agents' `SubAgent`** are the places found in this research where a `model`/`llm` override, a `tools` allowlist, and skill content can all be set on the same agent object (§3.1, §3.2, §3.3, §3.8). This is genuine, directly documented technical composition capability across all four — but in the first three, the skill list is a static, developer-configured, *eagerly*-loaded preload set at agent-definition time (eager for GitHub Copilot and Claude Code; also eager in CrewAI's common `Agent(skills=[...])` usage, per CrewAI's own docs). **Deep Agents' `SubAgent.skills` goes one step further:** the set of available skills is still statically configured, but their content is loaded via genuine runtime progressive disclosure within the subagent's own isolated `SkillsMiddleware`, and Deep Agents makes an explicit isolation claim ("not visible to the parent, and vice versa") that none of the other three make. Microsoft Agent Framework, by contrast, was not found to document any combined model+tools+skills schema at all — its Agents-as-Tools docs cover model/tools/context but do not mention Skills. None of the four combined-schema vendors' `skills` fields is the relevance-triggered, progressive-disclosure trigger (metadata-first, body-on-demand, *causing* invocation) that defines the "minimal Skill used only for discovery/routing" half of the composition in scope.
  - Delegation/handoff to another agent in general (without necessarily documenting all three properties together on the cited page) is additionally present in Google ADK's coordinator/subagent modes, OpenAI's Handoffs, Microsoft AutoGen's Handoffs pattern, Semantic Kernel's Handoff orchestration, and Microsoft Agent Framework's own Handoff and Workflows orchestration patterns.
- Routing across model cost tiers to reduce spend while preserving acceptable quality is supported by academic work (FrugalGPT, RouteLLM) as a general principle.

However, **no source found documents these elements combined into one named, first-class pattern in which a minimal, relevance-triggered Skill itself decides, at runtime, to invoke a cost-tiered subagent.** Of the frameworks surveyed, **Anthropic, LangChain (base library and Deep Agents), GitHub Copilot, Google ADK, CrewAI, and Microsoft Agent Framework** — six in total — document *both* a Skill-equivalent discovery mechanism and a subagent/delegation mechanism, and all six treat them as separate, independently described features rather than one named composed pattern. Among these, **LangChain's Deep Agents harness goes furthest at the technical-schema level and is this report's foregrounded closest comparator**, replacing GitHub Copilot and Claude Code as the "closest" reference point used in earlier drafts: Deep Agents' `SubAgent` definition documents a `model` override, an explicitly minimal `tools` allowlist, isolated per-subagent progressive-disclosure `skills` content, filesystem/artifact-write tools, and a structured JSON `response_format` — together, on one object, with LangChain's own docs recommending it as the built-in answer to "multi-agent." GitHub Copilot, Claude Code, and CrewAI remain the next tier, each combining a `model` override, a `tools` allowlist, and preloaded (eagerly-injected, not isolated) `skills` content on a single subagent/agent definition. Even in Deep Agents, however, that `skills` field is a static, subagent-definition-time list of what the subagent *may* draw on — not a progressive-disclosure Skill that the parent model discovers and decides, at runtime, to trigger as the reason for invoking the subagent; the trigger for invoking a Deep Agents subagent remains the parent's own reasoning over the `task` tool and the subagent's `description` field, entirely independent of skill loading. Microsoft Agent Framework documents both halves (§3.6) but, unlike the four vendors above, was not found to combine model/tools/skills into any single schema at all. The remaining frameworks reviewed (OpenAI's Agents SDK, Microsoft's legacy AutoGen, and Semantic Kernel) were confirmed in this research to document a subagent/delegation mechanism only — no Skill-equivalent progressive-disclosure mechanism was found documented for these three.

Critically, even having widened the set of frameworks confirmed to document a Skill-equivalent discovery layer to six, and having identified Deep Agents as a near-exact structural match for the *subagent* side of the composition, **none of the sources reviewed — including Deep Agents' own Subagents and Skills documentation — states that the outer composition in scope is itself a documented feature: that activation of a minimal, progressive-disclosure Skill is what instructs or causes the parent to invoke a separate, cheaper/tool-restricted subagent, which then writes a bounded artifact directly and returns a terse status.** Each vendor's Skills mechanism augments the *same* agent that discovered the skill (whether that agent is the main agent or, in Deep Agents' case, a subagent that has its own skill set for its own use), and each vendor's subagent/delegation mechanism is invoked independently of skill activation, driven instead by the parent's own reasoning over a delegation tool and the target subagent's description. This finding is unchanged by this update's broader search: it narrows the scope of what remains undocumented (from "no vendor combines model+tools+skills" to "no vendor documents a Skill's own activation as the cause of subagent invocation, even where model+tools+skills *are* combined on one object, as in Deep Agents"), rather than eliminating it. Based on the evidence gathered, this composition is best characterized as **a repository-local composition of established mechanisms, structurally closest to LangChain's Deep Agents `SubAgent` schema; the differentiating gap is narrowly the absence of a named, progressive-disclosure-Skill-triggered subagent pattern in the sources searched — not an absence of the underlying model/tools/skills composition capability, which Deep Agents, GitHub Copilot, Claude Code, and CrewAI's own schemas in fact support.**

This report makes **no claim of novelty, no claim of being "first," and no claim or assessment of freedom to operate.** It documents what was found (and explicitly, what was not found) as of the search date below, using the fixed queries and source catalogs logged in `search-log.md`. Absence of a documented prior combination is evidence of absence only within the scope, catalogs, and time searched — it is not proof that no such combination has been described elsewhere, and should not be relied upon for legal or IP purposes.

## 9. Limitations

- **Point-in-time snapshot.** Model availability (GPT-5.6 Sol, Claude Haiku 4.5) and their listed prices in GitHub Copilot are current as of the access date (2026-07-28) and are subject to change; the pricing figures cited are a snapshot, not a permanent fact. The same applies to the `deepagents` and Microsoft Agent Framework doc snapshots fetched in this update, both accessed 2026-07-28.
- **Search scope, not exhaustive coverage.** Sources were selected to match the categories the task specified (Anthropic/Claude, GitHub Copilot, OpenAI Agents SDK, LangChain/LangGraph including its Deep Agents harness, Google ADK, CrewAI, Microsoft's current Agent Framework and its legacy AutoGen/Semantic Kernel predecessors, relevant academic papers, context-engineering research, and gray literature on informal naming). Frameworks and papers outside these categories were not systematically searched.
- **One preprint is explicitly low-confidence.** arXiv 2604.21816 is very recent, non-peer-reviewed, and was verified only at the title/abstract level; it should not be treated as an established measurement (see §6).
- **Gray-literature sources are informal.** The two blog posts cited are individual practitioners' observations, not authoritative or peer-reviewed; they are included only to establish the absence of a settled informal name and to illustrate a conflation of rationales this report deliberately avoids (§5).
- **MCP (Model Context Protocol) was not independently researched.** It is mentioned only in passing where it appeared in an Anthropic source, since it is orthogonal to the specific skill+subagent composition in scope.
- **No legal analysis performed.** This report does not assess patents, trademarks, or freedom to operate, and none of its conclusions should be interpreted as legal advice or clearance.
- **Tool-schema token cost is not precisely quantified by any high-confidence, first-party source found.** Microsoft's "~100 tokens per skill" figure (§6) is the closest first-party number located, and it is explicitly treated as approximate, undocumented-methodology guidance rather than a measurement. See §6 for the full measured-vs-inferred breakdown.
- **This report reflects one completeness follow-up pass.** The omissions this pass corrected (LangChain Deep Agents, Microsoft Agent Framework) were identified by an external audit, not by this research's own initial catalog design; it remains possible that further passes would surface additional first-party sources not yet in scope (see `search-log.md` §6).
